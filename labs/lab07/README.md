# iBGP

### Задание

1. Настроить iBGP в офисе Москва между маршрутизаторами R14 и R15.
2. Настроить iBGP в провайдере Триада с использованием route reflector.
3. Настроить офис Москва так, чтобы приоритетным провайдером стал Ламас.
4. Настроить офис С.-Петербург так, чтобы трафик до любого офиса распределялся по двум линкам одновременно.
5. Все сети в лабораторной работе должны иметь IP-связность.

### 1. Схема

![](scheme.png)

| AS | iBGP-сессии | Особенности |
|---|---|---|
| 1001 Москва | R14 - R15 | Loopback0, next-hop-self, Ламас основной |
| 520 Триада | R23 (RR) - R24, R25, R26 | Loopback0, next-hop-self на пограничных R24, R26 |
| 2042 С.-Петербург | нет (один пограничный роутер) | `maximum-paths 2` на R18 |

### 2. iBGP в Москве

- **Сессия R14-R15 строится между Loopback0** (`update-source Loopback0`). Адреса Loopback известны через OSPF, и сессия не зависит от конкретного линка: R14 и R15 связаны только через R12 и R13, и при обрыве одного линка OSPF найдёт другой путь.
- **`next-hop-self`.** Без него R14 передал бы R15 маршруты с next-hop `101.0.0.1` (адрес Киторна на внешнем линке), которого нет в OSPF, и такие маршруты были бы недоступны.

### 3. Ламас как основной провайдер

Приоритет нужен в обе стороны.

**Исходящий трафик из Москвы.** На R15 всем маршрутам от Ламаса присваивается `local-preference 150` (по умолчанию 100). Local preference передаётся внутри AS по iBGP, поэтому и R14 выбирает маршруты через R15, хотя у него есть прямой eBGP-сосед Киторн.

Для внутренних сетей Москвы (R12, R13 и ниже) выход наружу задаёт маршрут по умолчанию в OSPF. R14 анонсирует его с метрикой 50, R15 с метрикой по умолчанию 1. Внутренний трафик уходит к R15, а R14 остаётся резервным выходом: если R15 перестанет анонсировать default, сработает default от R14.

**Входящий трафик в Москву.** Local preference действует только внутри своей AS. Чтобы чужие AS тоже предпочитали путь через Ламас, R14 удлиняет AS-path в сторону Киторна: `set as-path prepend 1001 1001`. Путь через Киторн становится длиннее пути через Ламас, и остальные AS выбирают Ламас.

### 4. iBGP в Триаде: route reflector

По правилу split horizon iBGP-роутер не передаёт маршруты, полученные по iBGP, другим iBGP-соседям. Поэтому без route reflector нужна полная связность (full mesh): для четырёх роутеров это шесть сессий. С route reflector каждому клиенту нужна только одна сессия, с RR.

- **Route reflector:** R23. Клиенты: R24, R25, R26.
- Сессии строятся между Loopback0, их адреса известны через IS-IS.
- **R24 и R26** (пограничные, у них есть eBGP-соседи) ставят `next-hop-self`: внешние адреса соседей не анонсируются в IS-IS.
- **RR передаёт маршрут, не меняя next-hop.** Поэтому трафик от R26 к Москве идёт сразу на R24, а не через R23. R23 участвует только в обмене маршрутами.

### 5. Балансировка в С.-Петербурге

R18 подключён к Триаде двумя линками (R24 и R26). Через route reflector R26 теперь тоже знает все внешние маршруты и анонсирует их R18. Поэтому R18 получает каждый префикс двумя одинаковыми путями (одна и та же AS-path, local preference, MED).

По умолчанию BGP устанавливает в таблицу маршрутизации только один лучший путь. Команда `maximum-paths 2` разрешает ставить до двух равноценных eBGP-путей, и трафик распределяется по обоим линкам.
